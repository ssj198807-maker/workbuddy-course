## 第 22 章 · 打造 Skill：将书和视频蒸馏为可执行 Skill

| 项 | 内容 |
|---|---|
| **课时** | 90 min |
| **难度** | ★★★★ |
| **核心目标** | 掌握"把外部知识变成内部能力" |
| **学习成果** | 1 个自创 Skill（基于一本书或视频） |

### 章节内容

#### 22.1 为什么需要自创 Skill（10 min）
- 现实：市场上 90% 的 Skill 满足不了你 10% 的特殊需求
- 自创 Skill 的三个动机：
  - **复用性**：你做 5 次的事情值得变 Skill
  - **团队化**：把"你会的东西"教给 AI 团队
  - **沉淀**：把"脑子里的判断标准"写下来

#### 22.2 Skill 的本质（15 min）
- Skill = **提示词 + 工具调用 + 输入输出校验 + 示例**
- 一个完整 Skill 应有的 4 件事：
  1. **触发条件**：什么场景下用
  2. **输入规范**：用户必须给什么
  3. **处理逻辑**：内部怎么跑（提示词 + 工具）
  4. **输出规范**：交付什么 + 验收标准

#### 22.3 三类 Skill 设计模式（30 min）

| 模式 | 适用 | 示例 |
|---|---|---|
| **提示词型** | 仅靠 LLM 就能完成 | 「降低 AI 腔」「标题优化」 |
| **工具型** | 需要调外部工具 | 「网页抓取」「PDF 转换」 |
| **混合型** | 提示词 + 工具 | 「公众号排版」（内容生成 + 图片生成） |

#### 22.4 从书/视频蒸馏 Skill（20 min）
**本章是三哥知识蒸馏方法论的工程化**：
- **步骤 1：拆骨架**——把书/视频的目录/章节拆出来
- **步骤 2：抽原则**——每个章节的核心原则是什么
- **步骤 3：写示例**——给 LLM 3-5 个示例（含正反例）
- **步骤 4：写校验**——输出必须满足什么
- **步骤 5：写提示词**——把所有上面这些串成 Skill
- **关键**：蒸馏不是抄，是"消化后输出"

#### 22.5 现场演示（10 min）
- 把《非暴力沟通》一本书蒸馏成「非暴力沟通对话改写」Skill
- 演示失败模式：示例不够、校验太严、提示词冗长

#### 22.6 与三哥知识蒸馏体系的连接（5 min）
- 三哥 wiki 有「AI 写作技能系统改造全记录」「AI 驱动的个人知识库革命」等笔记
- **三哥已经用同样方法做了一年 Skill 蒸馏**
- 学员可以参考三哥 wiki 的 `distill-to-content` skill 复用流程

### 教学要点
- ✅ **强调"少而精"——一个 Skill 不要覆盖太广**
- ✅ 引用三哥知识蒸馏经验作为参考
- ❌ 不要演示"全自动蒸馏"——必须人工审核

### 课后作业
- 蒸馏 1 个 Skill（基于你熟悉的一本书或视频）
- 跑通 3 个真实场景，迭代至少 2 版

## 第 23 章 · 其他用法补充：WorkBuddy 实操案例集

| 项 | 内容 |
|---|---|
| **课时** | 60 min |
| **难度** | ★★ |
| **核心目标** | 拓宽"AI 能做什么"的认知 |
| **学习成果** | 复刻 3-5 个补充案例 |

### 章节内容

#### 23.1 案例 1：简历生成（5 min）
- 输入：3 段经历 + 目标岗位
- 输出：3 个版本的简历（保守 / 标准 / 突破）
- 关键：**只用已有事实，不虚构经历**

#### 23.2 案例 2：会议录音 → 待办（10 min）
- 输入：30 min 会议录音
- 输出：纪要 + 5-10 条待办
- 关键：人名/数字必须二次确认

#### 23.3 案例 3：微信公众号排版发布（10 min）
- 输入：Markdown 原文
- 输出：HTML 排版 + 公众号草稿
- 关键：**绝不直接点"发布"**——必须人工

#### 23.4 案例 4：Excel 119 份门店数据清洗（10 min）
- 输入：119 份格式不一的 Excel
- 输出：1 份标准化数据 + 1 个交互看板
- 关键：先有清洗规则，不擅自补全

#### 23.5 案例 5：年报深度研究（10 min）
- 输入：1 家公司 10 年年报
- 输出：关键指标 10 年趋势 + 横向对比
- 关键：所有数字可追溯

#### 23.6 案例 6：GSAP 粒子动画网站（5 min）
- 输入：设计师的一句话需求
- 输出：完整 HTML + CSS + JS
- 关键：参考图必给、AI 简化 ≠ 客户原意

#### 23.7 案例 7：AI 资讯日报（5 min）
- 输入：5 个资讯源
- 输出：早 9 点飞书推送
- 关键：少而准（参第 15 章）

#### 23.8 案例选择决策表（5 min）
- 「想提升工作效率」→ 案例 1/2/3
- 「想学习商业 / 投资」→ 案例 5
- 「想做内容 / 自媒体」→ 案例 7
- 「想做数据 / 看板」→ 案例 4
- 「想做创意 / 设计」→ 案例 6

### 教学要点
- ✅ **每个案例都要给"踩坑清单"**
- ❌ 不要演示"花活"——重点是普适性

### 课后作业
- 复刻 1 个补充案例
- 输出：1 份你自己的"案例包"（任务说明 + 验收标准 + 踩坑清单）

## 第 24 章 · 多 Agent 系统设计 ★★★

| 项 | 内容 |
|---|---|
| **课时** | 120 min（拆为 2 节） |
| **难度** | ★★★★★ |
| **核心目标** | 从"几个 Agent 协作"升级到"多 Agent 系统设计" |
| **学习成果** | 1 份完整的多 Agent 系统设计文档 |

### 章节内容

#### 24.1 多 Agent 系统的本质（15 min）
- **为什么需要"多 Agent"而不是"一个大 Agent"**：
  - 单一 Agent 上下文窗口有限
  - 单一 Agent 任务多了容易"精神分裂"
  - 多 Agent 可以并行 + 专业化
- **多 Agent ≠ 多 Skill**：
  - Skill 是能力
  - Agent 是调度能力的协调器
  - 多 Agent 是协调器的协调

#### 24.2 三种多 Agent 架构（30 min）

```
1. 流水线型（Pipeline）
   Agent A → Agent B → Agent C → Agent D
   适合：流程固定的场景（如：内容生产流水线）

2. 协作型（Collaborative）
   ┌→ Agent A ─┐
   ├→ Agent B ─┼→ 协调器 → 输出
   └→ Agent C ─┘
   适合：多视角决策（如：投资分析）

3. 层级型（Hierarchical）
        团长 Agent
        /    |    \
   兵卒A  兵卒B  兵卒C
   适合：复杂任务分解（如：项目管理）
```

#### 24.3 消息协议与状态管理（20 min）
- 消息传递模式：
  - **同步**：Agent A 调 Agent B 等待结果
  - **异步**：Agent A 投递，Agent B 空闲时取
  - **广播**：团长发指令，所有兵卒收到
- 状态管理：
  - 共享状态（黑板模式）
  - 消息队列（事件驱动）
  - 数据库（持久化）

#### 24.4 失败处理与兜底（20 min）
- 三种失败：
  - **单 Agent 失败**：重试 + 跳过 + 告警
  - **消息丢失**：幂等设计 + 重投
  - **整体死锁**：超时机制 + 死锁检测
- **关键设计**：所有外部副作用必须**幂等**（重复执行结果一致）

#### 24.5 监控与可观测（20 min）
- 三类信号：
  - **业务信号**：任务成功率、平均耗时
  - **系统信号**：Agent 健康度、队列长度
  - **成本信号**：Token 消耗、API 调用次数
- 监控方式：
  - 日志：每个 Agent 的输入/输出/决策
  - 链路追踪：消息从进入到输出的完整路径
  - 告警：异常时通知人工

#### 24.6 现场演示（10 min）
- 设计一个 3-Agent 的"客户问题分类 + 处理"系统
- 演示失败模式：Agent 死循环、消息丢失、状态错乱

#### 24.7 与三哥 wiki《多 Agent 系统深度剖析》笔记的连接（5 min）
- 三哥 wiki 内 `多 Agent 系统深度剖析：从伪协同到真执行的技术突破与实践案例-0f24.md`
- 笔记里的关键判断：
  - "伪协同 vs 真协同"的判断标准
  - 多 Agent 落地的常见失败模式
- **学员必读这份笔记作为补充**

### 教学要点
- ✅ **强调"先单后多"**——单 Agent 跑通再上多 Agent
- ✅ 引用三哥多 Agent 笔记作为参考
- ❌ 不要陷入"协议设计"细节——本章是设计思维，不是工程实现

### 课后作业
- 写出 1 份"我的多 Agent 系统设计"文档
- 至少包含：架构图、消息流、失败处理、监控方案
- 跑通 1 个简化版（不需要全实现）

## 第 25 章 · 自动化工作流的可靠性

| 项 | 内容 |
|---|---|
| **课时** | 60 min |
| **难度** | ★★★★ |
| **核心目标** | 让自动化任务"敢睡个安稳觉" |
| **学习成果** | 1 份故障排查手册 + 1 套监控告警配置 |

### 章节内容

#### 25.1 自动化的 5 大风险（10 min）

| 风险 | 后果 | 频率 |
|---|---|---|
| **接口失效** | API 改版 / 平台限流 | 高 |
| **数据错误** | 输入脏数据 | 中 |
| **逻辑漏洞** | 边界条件没处理 | 中 |
| **资源耗尽** | Token / 配额用完 | 中 |
| **外部依赖** | 平台封号 / 服务停机 | 低 |

#### 25.2 可靠性设计 4 原则（20 min）

```
1. 幂等性    → 重复跑结果一样
2. 可重试    → 失败能自动重试
3. 可降级    → 关键路径挂了能用备选
4. 可观测    → 出问题能立刻知道
```

#### 25.3 故障排查流程（20 min）
```
告警 → 定位 → 修复 → 复盘 → 加防御
```

| 步 | 关键动作 | 工具 |
|---|---|---|
| 告警 | 配置多渠道（飞书/邮件/短信） | WorkBuddy 监控 |
| 定位 | 看日志 + 链路追踪 | 日志平台 |
| 修复 | 临时方案 + 永久方案 | - |
| 复盘 | 写"事后报告" | 文档 |
| 加防御 | 加测试 + 加监控 + 加重试 | - |

#### 25.4 常见故障案例（10 min）
- **案例 1：自动化任务跑了 100 次，突然全失败** → API Key 过期
- **案例 2：内容发布失败，重复跑导致重复发布** → 缺幂等设计
- **案例 3：夜间任务挂到天亮没人知道** → 没配告警
- **案例 4：Token 用完整个系统停摆** → 缺配额监控

### 教学要点
- ✅ 强调**"自动化不是不用管，是换一种管法"**
- ❌ 不要演示"全自动无人值守"

### 课后作业
- 写出 1 份"我的故障排查手册"
- 至少包含：5 类故障 + 4 类应对 + 3 条复盘要点
