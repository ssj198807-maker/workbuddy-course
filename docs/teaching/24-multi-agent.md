## 1. 多 Agent 系统的本质（15 min）

### 1.1 开场互动

讲师问：

> "**为什么需要'多 Agent'而不是'一个大 Agent'？**"

让 3-5 个学员回答（**不给标准答案**）。

讲师话术：

> "**单一 Agent 跑不动的时候，才需要多 Agent。**
> 不是越多越好。"

### 1.2 三个原因

| 原因 | 解释 |
|---|---|
| **上下文窗口有限** | 单一 Agent 上下文塞满就崩 |
| **任务多会精神分裂** | 让一个 Agent 又写脚本又剪辑，它就乱 |
| **并行 + 专业化** | 多 Agent 可以分工 + 同时跑 |

### 1.3 关键认知

| 概念 | 定义 |
|---|---|
| **Skill** | 能力（如：写文案、查天气） |
| **Agent** | 调度 Skill 的协调器（如：秘书小张） |
| **多 Agent** | 协调器的协调（如：项目部） |

讲师话术：

> "**多 Agent ≠ 多 Skill**——
> Skill 是能力，Agent 是协调器，多 Agent 是协调器的协调。
> 类比公司：员工 = Skill，经理 = Agent，部门 = 多 Agent。"

## 2. 三种多 Agent 架构（30 min）★ 本节重点

### 2.1 架构 1：流水线型（Pipeline）

```
Agent A → Agent B → Agent C → Agent D
```

**适用场景**：流程固定的场景
**典型示例**：内容生产流水线
**优点**：简单、可控、易调试
**缺点**：单点失败 = 整链失败

**设计要点**：
- ✅ 每个 Agent 任务必须明确
- ✅ 上游失败必须通知下游
- ✅ 失败重试有上限
- ✅ 全部成功才交付

### 2.2 架构 2：协作型（Collaborative）

```
   ┌→ Agent A ─┐
   ├→ Agent B ─┼→ 协调器 → 输出
   └→ Agent C ─┘
```

**适用场景**：多视角决策
**典型示例**：投资分析、面试筛选
**优点**：多视角、容错强
**缺点**：协调复杂、可能冲突

**设计要点**：
- ✅ 必须有"投票机制"或"权重机制"
- ✅ 必须有"冲突解决"规则
- ✅ 不能让所有 Agent 都说同样的话（多样性）
- ✅ 协调器必须有最终决策权

### 2.3 架构 3：层级型（Hierarchical）

```
      团长 Agent
      /    |    \
  兵卒A  兵卒B  兵卒C
```

**适用场景**：复杂任务分解
**典型示例**：项目管理、客服中心
**优点**：可扩展、职责清晰
**缺点**：团长是单点

**设计要点**：
- ✅ 团长必须能"理解任务"
- ✅ 团长必须能"合理拆解"
- ✅ 团长失败要有兜底
- ✅ 兵卒只听团长，不互相干扰

### 2.4 选型决策表

| 你的场景 | 推荐架构 |
|---|---|
| 流程固定（内容生产） | 流水线型 |
| 流程多变（投资分析） | 协作型 |
| 任务复杂（项目管理） | 层级型 |
| 都不确定 | 从流水线型起步 |

### 2.5 反模式（**必须警告学员**）

| 反模式 | 表现 | 后果 |
|---|---|---|
| **大杂烩型** | 10 个 Agent 各干各的 | 协调失败 |
| **单点依赖** | 全靠团长一个 | 团长挂全挂 |
| **无协调器** | Agent 之间直接调 | 死循环 |
| **过度设计** | 100 个 Agent | 维护崩溃 |

讲师话术：

> "**多 Agent 系统的成熟度标志**：
> - 第 1 阶段：3 个 Agent 跑通 1 个场景
> - 第 2 阶段：5 个 Agent 跨场景复用
> - 第 3 阶段：Agent 数量可扩展（10+）
> - 第 4 阶段：Agent 自组织（动态组队）
> 
> **绝大多数人死在第 2 阶段**——不要追求第 4 阶段。"

## 3. 现场演示 1（15 min）

### 3.1 演示场景

「客户问题分类 + 处理」3-Agent 系统

```
客户问题
   ↓
分类 Agent（判断类型：投诉/咨询/建议）
   ↓
    ├── 投诉 → 处理 Agent 1
    ├── 咨询 → 处理 Agent 2
    └── 建议 → 处理 Agent 3
                ↓
              反馈给客户
```

### 3.2 演示要点

- ✅ 演示 3 种不同输入 → 不同 Agent 处理
- ✅ 演示分类失败的兜底
- ✅ 演示消息日志（每个 Agent 的输入/输出）

### 3.3 演示失败模式
- ❌ 分类错误 → 给了错误 Agent
- ❌ 死循环 → Agent 互相调
- ❌ 状态丢失 → 处理后不知道处理到哪

## 4. 消息协议与状态管理（20 min）

### 4.1 消息传递三种模式

| 模式 | 描述 | 适用 |
|---|---|---|
| **同步** | A 调 B 等结果 | 强依赖场景 |
| **异步** | A 投递，B 空闲时取 | 队列场景 |
| **广播** | 团长发，所有兵卒收 | 通知场景 |

### 4.2 状态管理三种模式

| 模式 | 描述 | 适用 |
|---|---|---|
| **共享状态** | 黑板模式，Agent 读写同一处 | 简单场景 |
| **消息队列** | 事件驱动，状态随消息传 | 复杂场景 |
| **数据库** | 持久化，重启可恢复 | 关键场景 |

### 4.3 关键原则

讲师话术：

> "**所有外部副作用必须幂等**——
> 重复执行结果一致。
> 
> 例子：
> - 转账：必须幂等（不能转 2 次）
> - 发邮件：必须幂等（不能发 2 封）
> - 写数据库：必须幂等（不能写 2 条）"

---

## 5. 失败处理（20 min）

### 5.1 三种失败

| 失败 | 表现 | 兜底 |
|---|---|---|
| **单 Agent 失败** | Agent 跑挂 | 重试 + 跳过 + 告警 |
| **消息丢失** | 投递失败 | 幂等设计 + 重投 |
| **整体死锁** | 互相等 | 超时机制 + 死锁检测 |

### 5.2 失败处理 4 原则

```
1. 幂等性    → 重复跑结果一样
2. 可重试    → 失败能自动重试
3. 可降级    → 关键路径挂了能用备选
4. 可观测    → 出问题能立刻知道
```

### 5.3 重试策略

| 失败类型 | 策略 |
|---|---|
| **网络抖动** | 立即重试 1 次 |
| **临时限流** | 退避重试 3 次（间隔指数增长） |
| **数据错误** | 不重试，告警 |
| **系统错误** | 重试 1 次 + 告警 |

### 5.4 死锁检测

讲师话术：

> "**最简单的死锁检测是'超时'**——
> 每个 Agent 任务必须设最大执行时间（默认 5 分钟）。
> 超时即视为死锁，强制中断 + 告警。"

---

## 6. 监控与可观测（15 min）

### 6.1 三类信号

| 信号 | 例子 |
|---|---|
| **业务信号** | 任务成功率、平均耗时 |
| **系统信号** | Agent 健康度、队列长度 |
| **成本信号** | Token 消耗、API 调用次数 |

### 6.2 三种监控方式

| 方式 | 工具 | 作用 |
|---|---|---|
| **日志** | 日志平台 | 每个 Agent 的输入/输出/决策 |
| **链路追踪** | 追踪系统 | 消息从进入到输出的完整路径 |
| **告警** | IM 推送 | 异常时通知人工 |

### 6.3 告警分级

| 级别 | 触发 | 响应 |
|---|---|---|
| **P0** | 整系统挂 | 立即响应 |
| **P1** | 单 Agent 挂 | 1 小时内 |
| **P2** | 性能下降 | 当天 |
| **P3** | 异常但不影响 | 1 周内 |

---

## 7. 伪协同 vs 真协同：判断标准（5 min）

### 7.1 核心观点

讲师话术：

> "**多 Agent 落地的关键判断**——
> 核心观点：
> - **伪协同 vs 真协同**的判断标准
> - 多 Agent 落地的常见失败模式
> - 真协同的 3 个标志"

### 7.2 关键判断

| 伪协同 | 真协同 |
|---|---|
| 每个 Agent 独立决策 | 围绕共同目标 |
| 消息只在"打招呼" | 消息真的影响决策 |
| 失败无人感知 | 失败立即协调 |
| 优化只看单 Agent | 优化看整系统 |

## 8. 收尾（5 min）

### 课后作业

```
【作业 1：架构设计文档】
为你的业务设计 1 个多 Agent 系统
- 至少 3 个 Agent
- 必须明确架构（流水线/协作/层级）
- 必须有消息流图
- 必须有失败处理

【作业 2：跑通 1 个简化版】
- 不需要全实现
- 跑 1 个核心场景
- 写运行日志

【作业 3：写"多 Agent 复盘报告"】
- 跑 3 次后写
- 至少 3 条改进
- 至少 1 条边界
```

### 关键认知

- ✅ **多 Agent 不是越多越好**——单 Agent 跑不动才上
- ✅ **三种架构选型**——流水线/协作/层级
- ✅ **4 原则**——幂等/可重试/可降级/可观测
- ✅ **先少后多**——3 Agent 跑通 → 5 Agent 复用 → 10+ 扩展
